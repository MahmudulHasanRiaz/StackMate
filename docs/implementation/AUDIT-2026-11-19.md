## 1. Critical (2)

### API C-1 — Rate limiting is dead code in production
`rateLimitBuckets` Map lives inside `createStackMateApp()` (`app.ts:339`), but `index.ts:124-146` creates a fresh app on *every* `fetch()` and `scheduled()` call — the Map is always empty, `checkRateLimit` never trips. Sign-in brute force, forgot-password email bombing, invitation-token guessing, license activation — all unthrottled on the Worker. No per-account lockout exists either.
**Fix:** durable rate-limit store (KV / D1 / DB-backed bucket, keyed per IP + per account), enforced on auth + token endpoints; add per-account lockout. → Fix Batch A.

### API C-2 — Outbound webhooks and Meta CAPI are simulated, yet the DB records them as delivered
`defaultSimulatedTransport` (`webhooks/service.ts:323`) returns `{status: 200}`; the cron calls the dispatcher with no transport (`app.ts:5170-5173`), so production never contacts any receiver — but writes `delivered`/`delivered_at` rows. Zero `graph.facebook.com` calls exist in `apps/api/src`. This CORRECTS the earlier assumption that CAPI "records + queues honestly": it marks delivery that never happened. (DB F-07 is the same root cause on the CAPI branch: `webhooks/service.ts:382-393` sets `status="processed"`, `delivery_attempts += 1`, `delivered_at = now` with no Meta call. The UI honestly labels it "Processed (recorded)", but the DB column will mislead any future report/export.)
**Fix:** stop writing `delivered` for simulated transports — record `simulated`/`queued` honestly; real delivery (Batch 4) is the only path that may write `delivered`. → Fix Batch A.

## 2. High (17)

### API H-1 — Payment-evidence upload has NO permission check in either layer, no audit row
`app.ts:4054-4096`, `payments/service.ts:177-236`. Any `read_only` staff can attach files to any order.
**Fix:** require the payment permission + write an audit row. → Batch A.

### API H-2 — `media.view` / `media.manage` dead in the seed catalogue
Only 29 perms in `seed-reference.ts`; `validatePermissionAllowlist` 422s them, so no custom role can ever be granted media access; in-memory store 403s non-super_admin on all media endpoints (DB-backed prod has migration 0012 grants — seed↔migration drift).
**Fix:** add the two permissions to the seed catalogue + allowlist; reconcile seed vs migration. → Batch A.

### API H-3 — No way to suspend a staff member
Suspension checks exist everywhere but nothing can ever set `status` to `"suspended"` — no endpoint, no UI, no seed. A compromised staff account cannot be locked out through the product.
**Fix:** suspend/unsuspend endpoint + UI + audit. → Batch A.

### API H-4 — Staff creation has no validation at all
`POST /api/v1/admin/users` → `createStaffUserByAdmin`: 1-char passwords, unvalidated email, `TypeError` → 500 on malformed input.
**Fix:** validate (email format, password ≥10, role exists) → 422, never 500. → Batch A.

### API H-5 — Forgot-password fully unthrottled
The "per-email 60s cooldown" exists only as a comment (`app.ts:946-948`).
**Fix:** real cooldown + rate limit (with C-1). → Batch A.

### API H-6 — Site registration auto-marks the primary domain `verified` with zero DNS proof
`integrations/service.ts:84-87`. Batch 2 defect, still live.
**Fix:** real DNS verification (Batch 2 scope); until then, never auto-`verified`. → Batch A.

### API H-7 — No boot-time fail-closed check on URL vars
Production defaults to localhost URLs; `APP_ENV` defaults to `local`, silently enabling hardcoded dev secrets (`env.ts:118-161`).
**Fix:** fail boot when URL vars are localhost in staging/production. → Batch A.

### DB F-01 — Duplicate transaction reference can be approved twice → phantom credit
Two approvals of the same transaction reference both credit the customer.
**Fix:** unique constraint / serialized check on the reference at approval. → Batch B.

### DB F-02 — No unique index on `customers.normalized_email` / `normalized_phone`
App-level dedupe only; the `customers/service.ts:84-87` comment falsely claims DB enforcement. (API M-7, same root.)
**Fix:** add the unique index — needs staging duplicate cleanup first. → Batch B.

### DB F-03 — Refunds: table exists, no endpoint; cancel flow points staff at a workflow that does not exist
(API L-23, same root.)
**Fix:** refunds endpoint + cancel-flow copy that matches reality. → Batch B (scope = owner decision, §6).

### DB F-04 — A manual staff suspension can be silently auto-reactivated by the sweep
`transitionLicenseStatusByAdmin` (`licensing/service.ts:566-656`) writes an outbox event + audit log but never a `license_events` row, while `missedScheduleSuspendedLicenses` (`activation/service.ts`) decides reactivation purely from the latest `license_events` row. Sequence: missed-schedule suspend → admin resumes → admin suspends again → installment paid → next sweep reactivates a license the admin deliberately suspended. Directly contradicts the module's own documented guarantee ("Manual staff suspensions are never auto-reactivated").
**Fix:** manual suspend/resume must write `license_events` rows so the sweep's decision sees them. → Batch B.

### SPA H-01 — Every `ListTable` list page searches client-side, never server `?q=`
`lib/section-kit.tsx:111-121` (`useAdminList` takes no `q`), `:299-301` (`globalFilterFn` = `JSON.stringify(row.original).includes(needle)`). Affected: Customers, Orders, Products, Licenses, Subscriptions, Tickets, Leads, Staff, Payment Methods, Payment Review, Features, Packages, Integrated Sites, Credentials, Domains, Tracking Events, Audit Logs, Webhooks. Only safe today because the API returns the unbounded full collection (`app.ts:592-602`, `limit: null` = no cap) — the moment any endpoint caps/paginates, search silently misses rows.
**Fix:** debounced `q` threaded from `useAdminList` to `?q=`, per ADR-0010 Decision 1. → Batch C.

### SPA H-02 — Add Customer: over-long website/address passes client validation, then 422s AFTER the customer is created; retry hits a 409 dedupe conflict
`sections/customers.tsx:526` website `maxLength={500}` vs API `max(200)`; address lines `maxLength={300}` vs API `max(250)`; city/state `maxLength={150}` vs API `max(120)`. `validateCustomerForm` (`:370-388`) never checks length. `onSubmit` (`:759-780`) creates the customer first, then POSTs the address — address 422 goes to a generic `formError`, customer already exists; fixing the address and re-submitting → 409 "This email belongs to…".
**Fix:** align `maxLength` to the API caps (200/250/120) + length check in `validateCustomerForm`; ideally one request for customer+address. → Batch B.

### SPA H-03 — Five undocumented capped client-side filter combobox loaders
`loadListOptions` default `limit: 25` (`section-kit.tsx:131-155`), then client-side filter: `sections/leads.tsx:702-712` (assignee, `status === "active"`), `sections/orders.tsx:1908-1920` (wizard product picker), `:2329-2345` (wizard payment-method picker, `is_enabled`), `sections/payment-review.tsx:597-606` (payment-method picker), `sections/tickets.tsx:595-608` + `:902-915` (assignees). With 25+ matches, rank 26+ active records are invisible.
**Fix:** server-side `status=active` / `is_enabled=true` params, or record each as a bounded ADR-0010 exception. → Batch C.

### SPA H-04 — ADR exception (a) still live, `open_only` follow-up not implemented
`sections/payment-review.tsx:570-585` (`{ limit: 100 }` + client-side unpaid filter), ADR-0010 Decision 5. Repo-wide grep: `open_only` exists nowhere — the documented follow-up ("server-side `open_only` orders filter if order volume grows") was never built.
**Fix:** `?open_only=` on the orders endpoint, used by the loader. → Batch C.

### SPA H-05 — Audit-logs API has no `q` or `limit` at all; SPA loads every audit row ever
`apps/api/src/app.ts:5082-5108` — `GET /api/v1/admin/audit-logs` maps the whole `store.state.audit_logs`, no `parseListQuery`/`applyListLimit`; `sections/audit-logs.tsx:122-124` loads all of it; filter options derived from the loaded rows (`:136-148`).
**Fix:** server `?q=` + `?limit=` (+ server-side action/resource/outcome/actor filters), like the other list endpoints. → Batch C.

### SPA H-06 — Admin role cannot see "Staff & Roles" — deliberate seed policy, needs an owner decision
Nav gate is correct (`components/shell.tsx:211` gates `/staff` on `users.manage`); the `admin` role is deliberately seeded without it (`db/seeds/seed-reference.ts:66-68`, `db/migrations/0003_role_permission_grants.sql:13-20`); only `super_admin` holds it. Server agrees (`modules/identity/service.ts:258,997,1089,1233`); global-search Staff group is gated too (`modules/search/service.ts:46`). (API M-15, same root.) Not a code bug — a policy decision.
**Fix:** owner decides (§6): grant `admin` `users.manage` via a new migration + seed update, or document Super-Admin-only. → Batch E.
