# ADR-0009: Payment plans + partial payments, customer dedupe, license activation policy, renewal sweep, tickets, leads

- **Status:** Accepted (implemented 2026-11-17, Customer + Order batch — owner brief 2026-11-17 ~09:39 +06, design approved 11:02 +06, scope additions 11:03–11:09 +06)
- **Context:** Customers had no Add UI and orders had no Create UI (the create ENDPOINTS existed, the UI did not). Partial payments were hard-blocked by design (API spec §27: "Disabled for initial release unless product owner explicitly approves"); claims 422'd on any amount != total and approvals 422'd on any verified amount != total. Public checkout created a duplicate customer per order. Licenses were issued only on full-payment approval; there was no expiry/renewal automation (the cron drained only the outbox), no reminders, and nothing pushed license lifecycle to products. The owner approved the full design in one message thread and added, in order: financial overview + credit + staff reports (11:03), per-order billed/paid/due columns in the profile order list (11:06), Support Tickets (11:07) with optional linkages (11:08), Lead Management (11:09).

- **Decision 1 — Payment plans + partial payments (flips API spec §27):** Owner approval 2026-11-17 flips §27: multiple verified payments may settle one invoice. New table `order_installments` (migration 0009): order_id, installment_number, amount_minor, due_date (ISO YYYY-MM-DD), status pending/partially_paid/paid/overdue, paid_amount_minor, paid_at, notes. Three plan builders (`createInstallmentsForOrderInTx`, `payments/service.ts`): full (one installment, due = clearance date), advance+rest (advance amount XOR percent, rest due date), equal installments (N parts every X days from a start date; floor parts, remainder to the last). Due dates are editable after creation (`PATCH /api/v1/admin/orders/:orderId/installments/:installmentId`, audit `orders.installment.updated`). Claims + approvals accept ANY positive amount: 422 only for amount <= 0 (schema) or currency mismatch (`PAYMENT_AMOUNT_MISMATCH`); the old full-amount 422 is gone. Allocation is oldest-unpaid-installment first, unless the claim names an installment (`installment_id`, 422 `INVALID_INSTALLMENT` when it is not on this order or already fully paid). `order.payment_status` gains `partially_paid`; the invoice `partially_paid` path is now USED (amount_paid/due synced per verified payment, `paid_at` when fully paid). Paid/remaining are COMPUTED on read (`computeOrderPaid` — installment sums when installments exist, else succeeded-transaction sums; `computeOrderRemaining`) — no denormalized drift. An order completes only when fully paid. **Migration 0010 (found by the new tests, not by review):** the service set `partially_paid` but the 0000 DDL check on `orders.payment_status` still listed only ('unpaid','pending_verification','paid','partially_refunded','refunded') — the first partial approval failed in Postgres (`orders_payment_status_check`). 0010 drops and re-adds the check with 'partially_paid'. Invoices already included it; the 0009 tables carry plain text status columns with no check; subscriptions/licenses checks already include past_due/expired/suspended.
- **Decision 2 — Credit balance (owner scope addition 11:03):** A payment may exceed the order's remaining amount; the excess becomes the customer's credit (`customers.credit_balance_minor`, migration 0009), visible on the profile and in the list (Credit column). Credit is applied ONLY at approval time, explicitly: `ApprovePaymentSubmissionSchema.apply_credit_minor` (default 0), capped at the credit balance AND at the remaining amount (else 422 `CREDIT_EXCEEDS_BALANCE`) — never silent auto-apply. Settled = verified money + applied credit; the order's paid amount counts settled (so credit-applied money shows in paid/due), while the profile's "total paid" counts verified money only (`computeOrderPaidMoney`) — billed − paid(money) ≠ due when credit was applied, and credit is its own line, so the two views never silently disagree. `payment.approved` outbox event now carries the computed `payment_status`, not a hardcoded "paid".
- **Decision 3 — Customer dedupe + split (owner rules 10:36):** Normalized email and normalized phone each belong to AT MOST ONE customer. Matching (admin create, public checkout, inline order create): email match → that customer (new phone attaches as a secondary contact); phone match + new email → that customer (email attaches as secondary); neither match → new customer; both match DIFFERENT customers → 409 `CUSTOMER_CONTACT_CONFLICT` naming both customers, admin resolves, never auto-merge. Storage follows the repo's separate-table pattern: new `customer_contacts` (kind email|phone, normalized_value, UNIQUE (kind, normalized_value)) + `whatsapp` column on customers. **App-layer enforcement, not DB unique indexes on the primaries:** staging already holds duplicate primaries from the old checkout path and a unique index on `customers.normalized_email/phone` would fail the migration; the resolver (`resolveOrCreateCustomerInTx`) enforces the rule on all write paths, and a follow-up data-cleanup migration can add the unique indexes once staging duplicates are resolved. Phone normalization is E.164 (`normalizePhoneE164`: Bangladeshi `01…` 11-digit → `+880…`). Email-OR-phone is enforced at the contract schema (`CreateCustomerSchema.refine`) — WhatsApp alone does not satisfy it. Split (`POST /api/v1/admin/customers/:id/split-contact`): detaches a SECONDARY contact only (primary split 422s) into its own customer; the phone that moves with it defaults to the source's most recently added secondary phone, falling back to the primary phone (the "phone from the latest order placed with that email" default was NOT buildable — orders carry no contact email — so the expert default is the most-recently-added secondary phone; admin can pick a different phone in the dialog). If the picked phone is the source's primary it MOVES (source primary cleared); if secondary, that contact row is removed. Orders stay with the source customer (default; documented, not moved).
- **Decision 4 — License activation policy (owner answers 10:36):** Per-order columns (migration 0009): `activation_mode` (on_full_payment | on_percent | on_date), `activation_percent` (1–100), `activation_date`, `suspend_on_missed_schedule` (default false); `grace_days` on orders and subscriptions (default 3, editable per order). Semantics: on_full_payment → activate when paid == total; on_percent → activate when paid >= percent of total (threshold `ceil(total × percent / 100)`); on_date → activate on that date regardless of payment. If suspend_on_missed_schedule is ON and the license is active, a scheduled installment passing its due date unpaid suspends the license until that installment is paid, then auto-reactivates — ONLY missed-schedule suspensions auto-reactivate (manual staff suspensions never do; the latest license_event must be a "suspended" with reason "missed_schedule"). For on_full_payment the toggle is meaningless before activation (license not active yet) — the wizard says so. Evaluation points: payment approval (recompute activation + suspension) and the cron sweep (§5) for date-based activation and missed-schedule suspension. Every activation/suspension/reactivation writes a `license_event` + audit log entry (`licenses.license.activated/suspended/reactivated/expired`). **Renewal-grace reconciliation (§4 vs §5(d) tension, expert default):** a subscription goes active → past_due (inside the grace window, license keeps working) → expired (grace exhausted); the LICENSE is suspended at the same moment (license suspension is the enforcement; validate → 403 `LICENSE_SUSPENDED`); the license → expired when now > grace_until. Renewal payment revives both via the existing renewal flow. **Fulfillment re-run guard (pre-existing bug fixed):** `issueLicenseForOrderItemInTx` was already idempotent per order item, but `createOrExtendSubscriptionInTx` was not guarded for renewals — the old approval flow minted a DUPLICATE license on every renewal approval (a renewal item is a clone with a fresh id, so the old `source_order_item_id` guard never matched). `fulfillOrderItemsInTx` now reuses a non-revoked license already linked to the subscription instead of minting a duplicate.
- **Decision 5 — Renewal + expiry sweep + reminders (owner answers 10:36):** `handleScheduled` (after the load-bearing awaited outbox drain) runs `runRenewalExpirySweep` (new `modules/renewal/sweep.ts`): (a) date-based activation per order; (b) missed-schedule suspension/reactivation per order; (c) installments past due → overdue; (d) renewal detection — recurring active subscriptions whose period end is within the first reminder offset get a renewal invoice/order via the existing `generateRenewalInvoiceInTx` (idempotent via the pending-period check — a second run creates nothing and counts nothing); (e) subscriptions past period end → past_due inside grace, expired after grace (+ suspend its licenses); licenses past grace_until → expired + `license.expired` outbox event. The sweep is per-item try/catch with errors collected in the report — it never throws and never fails the outbox drain. **Reminders (Settings → Email):** offsets editable in the UI (due offsets default [7,1], overdue offsets default [1,3] with an on/off toggle), stored DB-side following the `general_settings` singleton pattern (`reminder_settings` row id `default`, load-only state collection + direct-Drizzle save like two_factor_policy/general_settings). Renewal reminders use the same offsets against `current_period_end`. Each reminder is sent once per (kind, reference_id, offset) — tracked in `sent_reminders` (UNIQUE (kind, reference_id, offset_days)). **Send-first-then-mark:** the sweep returns `reminders_due`; the caller sends each email and only then calls `markSweepRemindersSent` — a failed send retries on the next run instead of being silently lost. **Renewal orders get NO installments** (avoids a subscriptions→payments→activation→subscriptions import cycle; `computeOrderPaid` falls back to succeeded transactions for installment-less orders, so renewal approval still computes correctly). **First payment in the order wizard is NOT a backend field:** the wizard creates the order, then calls the existing staff-claim endpoint as a second request (compositional — avoids a nested-transaction deadlock); approval still happens via Payment Review, never auto-paid.
- **Decision 6 — Push to products + Integration Guide (owner answers 10:36):** License lifecycle is pushed through the EXISTING transactional outbox/webhook delivery path — no parallel sender. Events: `license.activated` / `license.suspended` / `license.reactivated` / `license.expired`, payload `{ license_number, product { id, name }, status, expires_at, grace_until, reason }`, signed per the existing `STACKMATE-WEBHOOK-V1` HMAC-SHA256 scheme. The in-app **Integration Guide** (Settings → Integration Guide, `sections/integration-guide.tsx`) documents the receiver contract, verified against code (not invented): license validate flow (`POST /api/v1/licenses/validate`, request/response, all 403 codes incl. `LICENSE_EXPIRED`/`LICENSE_SUSPENDED`/`INSTALLATION_NOT_ACTIVE`), the EdDSA JWS entitlement token (12h TTL, refresh at 6h via `next_validation_after`, claims incl. `entitlements` map + `activation_usage`, zero PII, verify signature + audience), activation limits (one `installation_id` = one seat; re-activation is an idempotent heartbeat; `ACTIVATION_LIMIT_REACHED`), the webhook receiver spec (headers, canonical string `STACKMATE-WEBHOOK-V1\n<ts>\n<delivery_id>\n<sha256hex(body)>`, `v1=` header, 300s timestamp tolerance, idempotency via `X-StackMate-Delivery`, 2xx within 10s), and the renewal prompt UX (plain language, renewal link, read-only mode, grace-window warning).
- **Decision 7 — Support Tickets (owner scope 11:07 + linkages 11:08):** New tables `support_tickets` + `ticket_comments` (migration 0009); ticket_number server-generated (`TKT-<sequence>`); customer_id nullable (unlinked reports allowed); title, description, status, priority (low/medium/high/urgent), category (small enum: billing/technical/license/order/other — expert default), reporter (staff user + source note), assignee_user_id (nullable staff), created/updated/resolved/closed_at. Comments: ticket_id, author_user_id, body, is_internal, created_at. Status flow open → in_progress → waiting_on_customer → resolved → closed, with reopen (closed/resolved → open, clears resolved/closed_at); enforced in the API (409 `INVALID_TICKET_TRANSITION`). Status + assignment changes are audit-logged. **Linkages (owner refinement 11:08):** order_id, subscription_id, license_id, product_id, all nullable. Picking an order auto-assigns its customer; picking a subscription/license auto-assigns customer + product; a manual customer disagreeing with the order's customer, or a subscription/license belonging to another customer, → 422 `TICKET_LINK_MISMATCH`. The create dialog keeps the primary flow clean (title + description + customer + priority + assignee) with the optional links in a collapsed "Linked records" section; the same grouped-section cleanliness applies to Add Customer and the Create Order wizard. Permissions: `tickets.view` / `tickets.manage` seeded like `customers.manage` (super_admin + admin both; support_staff both; read_only view). Customer profile gets an Issues tab (number, title, status, priority, assignee, updated) with full history; "Create issue" prefills the customer.
- **Decision 8 — Lead Management (owner scope 11:09):** New table `leads` (migration 0009): name, email, phone, whatsapp (optional), source_site_id (FK, nullable for manual), utm_source/medium/campaign, interest (free text + optional product_id link), message/notes, status (new → contacted → qualified → converted / lost), assignee_user_id, created/updated/converted_at, converted_customer_id + converted_order_id. Contact rule mirrors customers (at least one of email/phone). **Ingestion auth correction:** the brief said to reuse an existing `wpi_` Bearer token scheme — grep-verified 2026-11-17, NO such scheme exists anywhere in the codebase. The endpoint (`POST /api/v1/integrations/sites/:siteKey/leads`) reuses the EXISTING S2S HMAC auth (`authenticateSignedServerRequest`, scope `leads.create`, new capability added to `SITE_CAPABILITIES`), rate-limited like other integration endpoints (120/min). **Dedupe window (expert default):** same normalized contact from the same site within **30 days** → update the existing lead instead of duplicating; otherwise a new lead. **Tracking (honesty rule):** every API-ingested lead emits a Lead event into the existing tracking pipeline (`tracking_events` row, event_name "Lead", event_id `lead_<id>`, status "queued") + a `tracking.meta_capi.dispatch` outbox entry, on CREATE only (not on dedupe-update); manual leads (no site) emit none. Meta CAPI real delivery is a KNOWN STUB (docs-conformance audit) — the event is recorded + queued, never claimed as delivered. **Conversion (two-step, expert default):** `POST /api/v1/admin/leads/:id/convert` resolves/creates the customer via the §1 dedupe rules and returns it; the lead is NOT marked converted yet — the Create Order wizard opens with `?new=1&customer=<id>&lead=<id>` and order creation with `lead_id` marks it converted (converted_at + converted_customer_id + converted_order_id). Abandoning the wizard leaves the lead unconverted and the pre-created customer in place (harmless). Converting never deletes the lead. Direct orders from connected websites already flow via public checkout — nothing built there. **Circular FK:** `leads.converted_order_id` carries NO Drizzle `.references()` and NO SQL FK (plain uuid) — `orders.lead_id` already references leads; the link is enforced at service level (conversion writes it only after the order exists). Documented in code + here.
- **Decision 9 — Customer profile additions (owner scope 11:03 + clarification 11:06):** Profile shows a financial overview card (Total billed / Total paid / Total due / Credit balance, BDT) and 8 tabs: Orders, Subscriptions, Licenses, Payments, Connected Installations, Activity History, Issues, Reports. The Orders tab (order history list) shows Billed / Paid / Due as columns on EVERY row (owner clarification 11:06 — in the list, not only the detail). Staff reports: new `customer_reports` table (customer_id, author_user_id, type, detail required, created_at; audit-logged); types are exactly note / concern (small set, expert default); the list row shows a "Concern reported" warning badge when a concern report exists, the profile shows the same badge + a Reports tab listing all reports (author + date + detail) + a "File report" dialog. Connected Installations come from the `license.activations` nested in each license record (there is NO top-level `state.license_activations` collection); Activity History is the audit log filtered to the customer and their orders/subscriptions/licenses (last 100, newest first).
