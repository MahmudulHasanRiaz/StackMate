# ADR-0008: DB-driven auth config, Worker SMTP via `cloudflare:sockets`, restricted-session forced 2FA, OAuth linking, General Settings

- **Status:** Accepted (implemented 2026-11-16, Auth + Email batch — owner order 2026-11-16 ~13:12 + ~13:30 + ~15:39 +06)
- **Context:** Authentication configuration lived nowhere: no OAuth providers, no 2FA, no email system at all (grep for smtp / forgetPassword / sendResetPassword was zero). The owner ordered Settings-based BetterAuth configuration with OAuth + 2FA + provider-agnostic SMTP in one batch, plus General Settings (app name/title/favicon/description/support email). The Better Auth instance was built once per request already (`getBetterAuth(env, store)` builds a fresh instance per request in `handleRequest`) — the batch's "built once at module load" premise was wrong, which made DB-driven config easy.
- **Decision 1 — DB-driven auth config:** OAuth providers (`auth_oauth_providers`), 2FA policy (`auth_two_factor_policy`), and SMTP settings (`smtp_settings`, singleton) live in PostgreSQL (migration 0007). A Settings save takes effect without a redeploy: the auth instance is built per request from `loadAuthConfig` (module-level cache, 30s TTL, keyed by connection string, explicitly invalidated on save; other isolates converge within the TTL). The public `GET /api/v1/auth-config` endpoint reads the same source of truth, so the login page can never disagree with the auth instance. Secrets (OAuth client secrets, SMTP password) are encrypted at rest with AES-256-GCM under `ENCRYPTION_KEY_V1` (AAD `auth:oauth:<provider>` / `auth:smtp`) and never returned — GET views expose only `has_client_secret` / `has_password`.
- **Decision 2 — SMTP from a Cloudflare Worker via `cloudflare:sockets`:** Verified from Cloudflare's current docs (developers.cloudflare.com/workers/runtime-apis/tcp-sockets/, updated 2026-10-13): `connect()` with `secureTransport: "off" | "on" | "starttls"`, `socket.startTls()` for STARTTLS, sockets created inside a handler only. Port 25 is blocked — submission ports 465/587/2465/2525/2587 only; the settings UI rejects port 25. The client is a minimal hand-rolled SMTP client (EHLO → STARTTLS → AUTH LOGIN → MAIL/RCPT/DATA/QUIT) over `cloudflare:sockets`, dynamically imported (never a static top-level import — vitest runs in Node and would fail module resolution), with the `connect` function injectable so tests use a Node-net mock socket. No fake sender and no silent switch to one provider's HTTP API: the settings UI, queueing, templates, and all flows are built, and the transport is real; a real send still needs the owner's SMTP credentials (untested live — see the batch report). `wrangler.jsonc` needed no change (compatibility_date 2026-11-15 ≥ 2024-09-23, `nodejs_compat` already on).
- **Decision 3 — 2FA via better-auth 1.7.23 `twoFactor` plugin (TOTP + backup codes):** Verified from the installed package, not memory. The plugin's sign-in after-hook deletes the just-created session and returns `{ twoFactorRedirect: true }` with a signed `twoFactor` cookie — no session exists until verify succeeds. Backup codes are PLAINTEXT JSON by default, so `backupCodeOptions: { storeBackupCodes: "encrypted" }` is load-bearing. The TOTP secret is encrypted at rest by the plugin (`secretConfig` = `BETTER_AUTH_SECRET`). Policy is per-scope (`global` default + each of the 8 roles), strictest-wins (required > optional > off), default OFF. When the policy requires 2FA and the user has not set it up, the session is restricted server-side (403 `TWO_FACTOR_SETUP_REQUIRED` on every admin endpoint except `GET /api/v1/admin/me`) and the SPA shows the forced-setup wizard instead of the shell. A password reset NEVER disables 2FA; 2FA recovery is a separate purpose-bound token flow that verifies the password before disabling. **Session rotation:** `verify-totp` and `disable` both create a new session, delete the old one, and set the cookie — clients must follow the response's `set-cookie` (the test suite caught this; the SPA is same-origin so the browser handles it).
- **Decision 4 — OAuth linking, staff-only:** Only Google + GitHub are shipped (the same mechanism adds more; never invent a provider). `databaseHooks.user.create.before` ALWAYS returns false — Better Auth never creates users in StackMate; staff are provisioned by bootstrap/admin/invitation only, so a non-staff Google/GitHub login can never mint a user. Linking to an existing staff row happens only when the provider email matches and the local `email_verified` is true — all three provisioning paths set `email_verified: true`, so staff emails are admin-verified and implicit linking works with no change. `session.create.before` returns false for suspended staff (the OAuth equivalent of the credential sign-in suspension check); admin routes re-check staff status on every request anyway.
- **Decision 5 — Adapter schema key `twoFactors` (correction):** The first version passed the singular key `twoFactor` to the Drizzle adapter schema. That broke ALL sign-ins (`BetterAuthError: Drizzle schema mismatch — Missing tables: twoFactors`, thrown lazily on first twoFactor-model use). With `usePlural: true` the adapter expects the PLURAL camelCase keys (`users`, `sessions`, `accounts`, `verifications`, `twoFactors`) while the underlying Postgres table stays `two_factor`. Fixed by passing `twoFactors: twoFactorTable`. Any future claim about the adapter's expected schema keys must be verified against the installed `better-auth` dist, not assumed.
- **Decision 6 — General Settings (migration 0008):** App-wide config lives in the singleton `general_settings` row (id `default`); no seed writes it, so admin edits are never overwritten. The favicon is stored in R2 under the server-side key `branding/favicon-<sha256>.<ext>` (validated-private-object pattern, PNG/ICO/SVG ≤256 KB, magic-byte checked, SVG must not contain `<script>`) and served publicly via `GET /api/v1/favicon` — only the object key + content type + size live in the row, never the bytes and never a data URL. Every value renders somewhere visible (brand, tab title, favicon, login tagline + support contact, meta description); currency/timezone/language are NOT settings (BDT + Asia/Dhaka fixed by spec, admin English-only).
- **Decision 7 — Fix batch (2026-11-16): origin check pinned ON; auth-config view; no fake "sent" (three live failures, one root pattern — the stub masked all three):** (a) **Origin check:** Better Auth defaults `skipOriginCheck` to `isTest() ? true : false`, and `isTest()` is true under vitest via BOTH `NODE_ENV=test` and `TEST=true` (vitest sets it) — no env tweak can turn the check on in tests, so the suite never exercised it while production (Workers) enforced it, hiding the live 2FA 403. The product pins `advanced.disableOriginCheck: false` in `createBetterAuth` — behavior-preserving in production (already on there), and it makes tests exercise the real check. `trustedOrigins` additionally always includes the app's own deployment origins (`API_URL`/`APP_URL`) so a stale `BETTER_AUTH_URL` can never lock the same-origin SPA out. (b) **Auth-config view:** `GET /api/v1/admin/auth-config` returned the raw `ResolvedAuthConfig` — camelCase `twoFactorPolicy` (crashed the Settings page: `config.two_factor_policy` undefined) AND the decrypted OAuth `clientSecret` / SMTP `password`. It now returns the snake_case `AuthConfigView` via `toAuthConfigView` (defaults on empty, secrets never returned), and the page normalizes defensively. (c) **Forgot-password honesty:** the endpoint stays generic-200, but mints NO token row when SMTP is not configured (same for 2FA recovery), and the forgot/recovery pages read the public `email_configured` flag and say plainly when email is not configured instead of the fake "a reset link has been sent". (d) **Harness rule (applies to every future batch):** a stub that returns a fuller shape than the real API hides bugs — the audit stub now has a `signed-in-empty` mode returning the exact empty view, and new flows get a real-API-backed vitest where the stub cannot prove the behavior.
- **Decision 8 — Fix batch #2 (2026-11-16): normalize every trusted origin; the batch-#1 origin fix did not hold live (correction to Decision 7a):** Batch #1 proved "API_URL origin → 200 + QR" in vitest — the happy path only. Live, the 2FA password gate still 403'd, now with Better Auth's flat "Invalid origin" (INVALID_ORIGIN). Verified root cause, against the INSTALLED better-auth 1.7.23 dist: `matchesOriginPattern` (dist/auth/trusted-origins.mjs) compares a non-wildcard trusted-origin pattern with EXACT string equality against `getOrigin(url)` — the pattern is never normalized — while `getTrustedOrigins` (dist/context/helpers.mjs) pushes `options.trustedOrigins` RAW. A dashboard `TRUSTED_ORIGINS` entry copied with a trailing slash or a path can therefore never match the browser's bare Origin header, and `env.ts` silently falls back to `http://localhost:8787` when `API_URL`/`APP_URL` are unset (no error, no log), leaving only the raw list. The rule from now on: EVERY trusted origin goes through `normalizeTrustedOrigin` (`new URL().origin`, which also lower-cases the host and drops default ports and paths) — `TRUSTED_ORIGINS` entries, plus explicit `originOf(BETTER_AUTH_URL)` (never rely on Better Auth auto-trusting baseURL alone), plus `originOf(API_URL)`/`originOf(APP_URL)`. Wildcard patterns (`*`/`?`) are kept verbatim (trimmed): they are Better Auth's own matching syntax and `new URL()` rejects a bare `*.example.com`, so normalizing one would silently drop it. The `disableOriginCheck: false` pin is unchanged. Any future claim about how Better Auth matches origins must be verified against the installed dist, not assumed — and any origin test must cover the dashboard shapes (trailing slash, unset API/APP vars, stale baseURL), not just the clean happy path.
- **Decision 9 — 2FA origin DIAGNOSIS (2026-11-16): the live failure is the missing-vars env shape, and both earlier fixes targeted the wrong premise (correction to Decisions 7a and 8):** Fix #2 also failed live (clean re-test after the deploy finished, "mid-rollout" dead). A diagnosis batch traced the exact request path (SPA `rawApiRequest` → Worker `fetch` → `handleRequest` → `getBetterAuth` → `auth.handler(ORIGINAL request)` — zero `new Request` in `apps/api/src` — → better-call router → `originCheckMiddleware` on `/**` → `validateOrigin`, which re-computes the trusted list per request from the same init options; no dynamic-baseURL path) and proved the mechanism in a new vitest suite (`two-factor-origin-diagnosis.test.ts` 12/12, full dispatcher, real Postgres + real Better Auth): the `$context.trustedOrigins` list and the HTTP result for every env shape — all-correct → 200 + QR; TRUSTED_ORIGINS-only → 200 + QR; TRUSTED_ORIGINS-empty (others cover) → 200 + QR; **all-localhost (every URL var at its `env.ts` fallback) → 403 INVALID_ORIGIN, the exact live error**. The live trusted list therefore contains only localhost origins: the dashboard URL vars (`BETTER_AUTH_URL`, `API_URL`, `APP_URL`, `TRUSTED_ORIGINS`) are NOT reaching the staging Worker environment. Both earlier fixes were wrong in premise, not in code: they assumed `TRUSTED_ORIGINS` was correct live because state-changing admin POSTs succeed live — but that inference was invalid, because the app's own CSRF gate (`app.ts:1814`) is BLIND live: `parseSessionCookie` (`app.ts:190`) recognises only `stackmate_session`, `__Host-stackmate_session` and the bare `better-auth.session_token`, while staging/production actually sets `__Secure-better-auth.session_token` (`useSecureCookies: isProd`, installed dist `dist/cookies/index.mjs:23`; Better Auth's own parser checks the `__Secure-` name first, so its check fires normally). The gate's `sessionCookie && …` condition is therefore never true live, so admin POSTs pass whatever `env.TRUSTED_ORIGINS` holds. The fix for 2FA is CONFIG, not code: set all four vars to the Worker URL in the Cloudflare dashboard (CORRECTION 2026-11-16 ~18:51, browser-verified: there is NO "Staging" environment in the dashboard for this service — only Production + Previews Base; the service's Production env IS the staging Worker's runtime env, so the vars were set under Production; the original "staging environment" wording here was wrong); any one naming the origin suffices, all four is belt-and-braces. NO product-code change ships for 2FA in this batch — a third code fix would be another guess. **Second finding (security hole, NOT shipped — sequencing):** the dead CSRF gate means a cross-site POST with the victim's cookies currently passes the app's `/api/v1/admin/*` protection in staging/production. The exact fix is one line (add `"__Secure-better-auth.session_token"` to `parseSessionCookie`), but it must ship ONLY after the dashboard vars are confirmed set — once the gate can see the cookie it enforces, and with the all-localhost env every state-changing admin call would 403 live. **Lesson (hard, from this saga):** a vitest-passed origin fix is NOT live proof, and a "proof" that rests on another gate must first prove THAT gate fires live — in vitest (`APP_ENV=test`) the cookie has no `__Secure-` prefix, so the gate fired and the S2 shape passed, hiding the live difference entirely. Any future origin claim must cover the staging cookie shape too.
- **Decision 10 — Follow-up batch (2026-11-16): durable URL vars in `wrangler.jsonc` + the CSRF gate finally sees the staging cookie (closes decision 9's second finding):** Two things landed together, and the ordering is load-bearing. (a) **Durable vars:** the four URL vars (`BETTER_AUTH_URL`, `API_URL`, `APP_URL`, `TRUSTED_ORIGINS` = `https://stackmate-api-staging.ad-dawah.workers.dev`) now live in `apps/api/wrangler.jsonc` `env.staging.vars` ONLY — never top-level vars (production is not set up and its URL is unknown; never invent a production URL). Dashboard-set plain vars are NOT durable: a Git-build deploy WIPES every plain var not in `wrangler.jsonc` — observed live, the diagnosis push's build `1544e07f` reverted the Worker from 15 vars back to 11, dropping all four; they had to be re-added by hand, and the next build would have wiped them again. The four values are plain URLs, not secrets, so committing them is safe; the five real secrets stay dashboard-only. (b) **CSRF-gate fix:** one line — `"__Secure-better-auth.session_token"` added to `parseSessionCookie` (`app.ts:190`), so the app's own CSRF gate (`app.ts:1814`) can finally see the cookie staging/production actually sets and enforce: a cookie-authenticated state-changing request from an untrusted Origin now 403s with "blocked by CSRF policy". This ships ONLY now because the vars are durable first — had the gate fix deployed while the dashboard vars were still wipeable, the first Git build after it would have wiped the vars AND the newly-enforced gate would have 403'd every admin POST live. Verified in a new focused suite (`csrf-gate-secure-cookie.test.ts` 3/3, full dispatcher, real Postgres + real Better Auth, `APP_ENV=staging`, all four vars naming the staging origin): same-origin PATCH `/api/v1/admin/me` with the `__Secure-` cookie → 200; cross-origin PATCH with the cookie + untrusted Origin → 403 (this row FAILED before the fix — the blind gate let it through as 200 — and passes after); 2FA enable with the vars set → 200 + QR (no regression). The diagnosis suite's staging-shape test is updated to match: its PATCH assertion changes 200 → 403, because the gate it proved blind now enforces. Live proof owed after push: confirm the 4 vars survive the Git build (dashboard check or 2FA gate re-test) and that admin POSTs still work with the gate enforced.
- **Decision 11 — SMTP fix batch (2026-11-16): test-email hang bounded, SMTP gets its own menu, 2FA policy labels unclipped, and the ~1/min cron exception was a missing `await`:** (a) **SMTP client timeouts:** before this batch only the socket read had a timeout (`READ_TIMEOUT_MS` 10s); `connectImpl()`, every `writer.write()`, `socket.startTls()`, and `socket.close()` in `finally` could wait forever — that is why the live "Send test email" button stuck on "Sending…" 90s+ with no success and no error while the Worker held no request anywhere near 90s (P99 ~2s). Now every step is bounded at 10s (`STEP_TIMEOUT_MS = READ_TIMEOUT_MS`) and the whole send runs under a 60s total budget (`TOTAL_SEND_TIMEOUT_MS`); every failure surfaces as an `SmtpError` with the real cause, never credentials in the message. The admin `apiRequest`/`rawApiRequest` helpers also gained a 30s client-side timeout (`AbortSignal.timeout` → `REQUEST_TIMEOUT`), so no button can stick forever. (b) **SMTP own menu (owner order):** SMTP configuration is now its own Settings menu at `/settings/email` (group General, permission `users.manage`); Settings → Authentication keeps OAuth + 2FA policy only. API paths are UNCHANGED — the move is UI-only; the forgot-password and 2FA-recovery pages now point at "Settings → Email". (c) **2FA policy labels:** `.sm-policy-row .sm-select { width: auto; flex: none; }` (the F3 toolbar pattern) — the full-width select was squeezing `.sm-policy-label` (flex:1, min-width:0) until "Super Admin" rendered "Su/Ad". (d) **The ~1/min uncaught exception — a missing `await`, not the cron's work:** `handleScheduled` did `return processTransactionalOutboxBatch(...)` WITHOUT `await` inside a `try/finally` that closes the store. In an async function the `finally` runs before the returned promise settles, so the store's pg client was ended while the outbox drain was still running and its first `BEGIN` threw "Client was closed and is not queryable" — every cron invocation failed and the outbox NEVER drained on schedule (2.59k invocations / 1.4k errors in 24h). The fix is one word: `return await processTransactionalOutboxBatch(...)`. The fetch path was never affected (`fetchHandler` already uses `return await handleRequest(...)`). Proved test-first: the new `scheduled-cron.test.ts` (4/4, exact live path — full dispatcher, real Postgres, staging-shaped env) FAILED 4/4 before the fix and PASSES 4/4 after. **Lesson:** `return <promise>` inside `try/finally` is a trap — the `finally` runs first; any async function that must finish work before its cleanup runs needs `return await`.
- **Decision 12 — SMTP follow-up fix (2026-11-16): raw transport errors are normalized to SmtpError with the real cause — the generic "Email could not be sent." never hides a failure again:** Live re-test ~22:16 +06 (staging build ea5c65a6, commit f5e09765): "Send test email" now SETTLED (hang fixed) but failed with the red inline error "Email could not be sent." That string exists ONLY at `service.ts:103` — the non-SmtpError fallback in `sendStackMateEmail`'s catch — so the throw inside `sendMailViaSmtp` was definitively a NON-SmtpError. The owner checked his Gmail thoroughly: the test mail did NOT arrive, so the send fails BEFORE Gmail accepts (before or at DATA), not post-accept — the QUIT/close path is ruled out as the failure point. The remaining unwrapped paths were: `socket.writable.getWriter()` / `readable.getReader()` (synchronous throws), raw rejections from `reader.read()` inside `readChunk` (a stream error rejects with a raw TypeError/DOMException), and raw rejections from `writer.write()` inside `withTimeout` (the race rejects with the raw error; only the timeout is wrapped). Fix: `asSmtpError(err, step, prefix?)` in `smtp-client.ts` normalizes EVERY throw leaving `sendMailViaSmtp` to SmtpError carrying the real transport cause (error name + message), format `SMTP <step> failed (<Name>: <message>).` — e.g. `SMTP read failed (TypeError: …).`, `SMTP write failed (Error: …).`, `SMTP stream setup failed (TypeError: …).`; connect/startTls keep their established messages with the cause appended in parentheses, so existing assertions still match. An outer safety net around the total-budget return converts anything the targeted conversions miss. Credentials can never appear: stream errors carry runtime state only (we never send credentials except as base64 AUTH lines, which never surface in a stream error), and the AUTH exchange itself still only ever yields reply codes. The service's generic fallback stays as a safety net but is now unreachable for send errors. Proved by 7 new tests in `smtp-client.test.ts` (4 client-level in-memory + 3 at the `sendStackMateEmail` level against a real Postgres DB seeded via `saveSmtpSettings`, each asserting the error names the cause and is NOT "Email could not be sent."). The next live test click should show the REAL cause — the parent live re-tests after push; Gmail delivery itself is still unproven until then.
- **Decision 13 — SMTP write-lock fix (2026-11-16): release the old reader/writer BEFORE `startTls()`, never after — workerd's upgrade flushes a writable that must be unlocked:** Live re-test ~22:53 +06 (staging build 2798dce0, commit ec6a31e9, Gmail smtp.gmail.com:587 STARTTLS, App Password): "Send test email" settled ~4–10s with the exact error `SMTP write failed (TypeError: This WritableStream is currently locked to a writer.).` — the error-surfacing fix (Decision 12) working, this is the real cause, pre-DATA (mail never arrived). **Proved mechanism, from the workerd source (not the docs, which never state it):** `Socket::startTls()` (`src/workerd/api/sockets.c++`, L2179–2181) calls `writable.flush(js)` on the CURRENT socket's writable and chains the detach + TLS upgrade as the flush's `.then()` continuation — so the upgrade only proceeds once the flush settles. `WritableStream::flush()` (`src/workerd/api/streams/writable.c++`, L431–443) returns a rejected promise with exactly `TypeError: "This WritableStream is currently locked to a writer."` whenever the stream is locked to a writer. The client held the writer lock across `startTls()` (it released the old reader/writer only AFTER the call), so the flush rejected immediately; that rejection propagates through `context.awaitJs` into the new socket's promised stream, erroring the new socket's readable/writable with that TypeError — while `startTls()` itself returns the new Socket synchronously and never throws. The first post-upgrade write (EHLO) then rejects with the stored error. Reproduced under local workerd (wrangler dev, against real smtp.gmail.com:587 — the sandbox intercepts outbound SMTP, so the peer is dead after the greeting, but the discriminator is exact): order=after (current code) → post-upgrade EHLO write AND read both fail with `TypeError: This WritableStream is currently locked to a writer.`; order=before (fix) → the lock error is GONE, the write instead fails with `TypeError: This WritableStream has been closed.` (the interceptor-killed peer — an artifact of the sandbox, not the client). **Fix (minimal, `smtp-client.ts` only):** move the two releases to BEFORE the `startTls()` call — `reader.release()` then `writer.releaseLock()` (try/catch, already-released is a no-op), then `socket = socket.startTls()`, then `openStreams(socket)`. Safe because every write has been awaited by then (each `sendCommand` awaits), so the queue is drained and `startTls` flushes the now-unlocked stream itself. Timeouts (10s step / 60s total / 30s client) and error normalization are untouched; no API, UI, or migration change. **Proved test-first:** a new workerd-faithful mock in `smtp-client.test.ts` whose `startTls()` reads the live `writable.locked` flag — locked at upgrade → the returned socket's streams error with the exact workerd TypeError; unlocked → healthy — so the older fresh-streams mocks (which cannot see this bug) are no longer the only coverage. The new end-to-end STARTTLS test FAILED before the fix with the exact live error (`SMTP write failed (TypeError: This WritableStream is currently locked to a writer.).` from the post-upgrade EHLO) and PASSES after; a regression-guard test asserts the mock itself errors a locked upgrade, so the reproduction can never go vacuous. **Lesson:** `startTls()` returning a socket does not mean the upgrade succeeded — its failure is deferred into the new socket's streams. Any future socket-upgrade code must release all locks before the call, and any mock of `startTls` must model the flush rule (locked → errored new socket), not just return fresh streams.
- **Consequences:** Auth config changes take effect within 30s cluster-wide with no redeploy. SMTP works from the Worker with no third-party HTTP API, at the cost of a hand-rolled client that must be maintained (and tested against the mock socket). 2FA is enforced server-side, not by UI hiding. The `twoFactors` key is a known adapter quirk — if better-auth changes its pluralization, the sign-in suite fails loudly (it did) rather than silently.
- **Alternatives considered:** (a) Env-var config for OAuth/SMTP — rejected: the owner ordered UI-based config in Settings, never via ENV (same rule as tracking pixel-groups). (b) One provider's HTTP email API — rejected: the owner ordered provider-agnostic SMTP. (c) Forced-2FA by UI gate only — rejected: a restricted session must be enforced server-side or a direct API call bypasses it.
