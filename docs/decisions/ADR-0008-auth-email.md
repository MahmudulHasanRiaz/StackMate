# ADR-0008: DB-driven auth config, Worker SMTP via `cloudflare:sockets`, restricted-session forced 2FA, OAuth linking, General Settings

- **Status:** Accepted (implemented 2026-11-16, Auth + Email batch — owner order 2026-11-16 ~13:12 + ~13:30 + ~15:39 +06)
- **Context:** Authentication configuration lived nowhere: no OAuth providers, no 2FA, no email system at all (grep for smtp / forgetPassword / sendResetPassword was zero). The owner ordered Settings-based BetterAuth configuration with OAuth + 2FA + provider-agnostic SMTP in one batch, plus General Settings (app name/title/favicon/description/support email). The Better Auth instance was built once per request already (`getBetterAuth(env, store)` builds a fresh instance per request in `handleRequest`) — the batch's "built once at module load" premise was wrong, which made DB-driven config easy.
- **Decision 1 — DB-driven auth config:** OAuth providers (`auth_oauth_providers`), 2FA policy (`auth_two_factor_policy`), and SMTP settings (`smtp_settings`, singleton) live in PostgreSQL (migration 0007). A Settings save takes effect without a redeploy: the auth instance is built per request from `loadAuthConfig` (module-level cache, 30s TTL, keyed by connection string, explicitly invalidated on save; other isolates converge within the TTL). The public `GET /api/v1/auth-config` endpoint reads the same source of truth, so the login page can never disagree with the auth instance. Secrets (OAuth client secrets, SMTP password) are encrypted at rest with AES-256-GCM under `ENCRYPTION_KEY_V1` (AAD `auth:oauth:<provider>` / `auth:smtp`) and never returned — GET views expose only `has_client_secret` / `has_password`.
- **Decision 2 — SMTP from a Cloudflare Worker via `cloudflare:sockets`:** Verified from Cloudflare's current docs (developers.cloudflare.com/workers/runtime-apis/tcp-sockets/, updated 2026-10-13): `connect()` with `secureTransport: "off" | "on" | "starttls"`, `socket.startTls()` for STARTTLS, sockets created inside a handler only. Port 25 is blocked — submission ports 465/587/2465/2525/2587 only; the settings UI rejects port 25. The client is a minimal hand-rolled SMTP client (EHLO → STARTTLS → AUTH LOGIN → MAIL/RCPT/DATA/QUIT) over `cloudflare:sockets`, dynamically imported (never a static top-level import — vitest runs in Node and would fail module resolution), with the `connect` function injectable so tests use a Node-net mock socket. No fake sender and no silent switch to one provider's HTTP API: the settings UI, queueing, templates, and all flows are built, and the transport is real; a real send still needs the owner's SMTP credentials (untested live — see the batch report). `wrangler.jsonc` needed no change (compatibility_date 2026-11-15 ≥ 2024-09-23, `nodejs_compat` already on).
- **Decision 3 — 2FA via better-auth 1.7.23 `twoFactor` plugin (TOTP + backup codes):** Verified from the installed package, not memory. The plugin's sign-in after-hook deletes the just-created session and returns `{ twoFactorRedirect: true }` with a signed `twoFactor` cookie — no session exists until verify succeeds. Backup codes are PLAINTEXT JSON by default, so `backupCodeOptions: { storeBackupCodes: "encrypted" }` is load-bearing. The TOTP secret is encrypted at rest by the plugin (`secretConfig` = `BETTER_AUTH_SECRET`). Policy is per-scope (`global` default + each of the 8 roles), strictest-wins (required > optional > off), default OFF. When the policy requires 2FA and the user has not set it up, the session is restricted server-side (403 `TWO_FACTOR_SETUP_REQUIRED` on every admin endpoint except `GET /api/v1/admin/me`) and the SPA shows the forced-setup wizard instead of the shell. A password reset NEVER disables 2FA; 2FA recovery is a separate purpose-bound token flow that verifies the password before disabling. **Session rotation:** `verify-totp` and `disable` both create a new session, delete the old one, and set the cookie — clients must follow the response's `set-cookie` (the test suite caught this; the SPA is same-origin so the browser handles it).
- **Decision 4 — OAuth linking, staff-only:** Only Google + GitHub are shipped (the same mechanism adds more; never invent a provider). `databaseHooks.user.create.before` ALWAYS returns false — Better Auth never creates users in StackMate; staff are provisioned by bootstrap/admin/invitation only, so a non-staff Google/GitHub login can never mint a user. Linking to an existing staff row happens only when the provider email matches and the local `email_verified` is true — all three provisioning paths set `email_verified: true`, so staff emails are admin-verified and implicit linking works with no change. `session.create.before` returns false for suspended staff (the OAuth equivalent of the credential sign-in suspension check); admin routes re-check staff status on every request anyway.
- **Decision 5 — Adapter schema key `twoFactors` (correction):** The first version passed the singular key `twoFactor` to the Drizzle adapter schema. That broke ALL sign-ins (`BetterAuthError: Drizzle schema mismatch — Missing tables: twoFactors`, thrown lazily on first twoFactor-model use). With `usePlural: true` the adapter expects the PLURAL camelCase keys (`users`, `sessions`, `accounts`, `verifications`, `twoFactors`) while the underlying Postgres table stays `two_factor`. Fixed by passing `twoFactors: twoFactorTable`. Any future claim about the adapter's expected schema keys must be verified against the installed `better-auth` dist, not assumed.
- **Decision 6 — General Settings (migration 0008):** App-wide config lives in the singleton `general_settings` row (id `default`); no seed writes it, so admin edits are never overwritten. The favicon is stored in R2 under the server-side key `branding/favicon-<sha256>.<ext>` (validated-private-object pattern, PNG/ICO/SVG ≤256 KB, magic-byte checked, SVG must not contain `<script>`) and served publicly via `GET /api/v1/favicon` — only the object key + content type + size live in the row, never the bytes and never a data URL. Every value renders somewhere visible (brand, tab title, favicon, login tagline + support contact, meta description); currency/timezone/language are NOT settings (BDT + Asia/Dhaka fixed by spec, admin English-only).
- **Consequences:** Auth config changes take effect within 30s cluster-wide with no redeploy. SMTP works from the Worker with no third-party HTTP API, at the cost of a hand-rolled client that must be maintained (and tested against the mock socket). 2FA is enforced server-side, not by UI hiding. The `twoFactors` key is a known adapter quirk — if better-auth changes its pluralization, the sign-in suite fails loudly (it did) rather than silently.
- **Alternatives considered:** (a) Env-var config for OAuth/SMTP — rejected: the owner ordered UI-based config in Settings, never via ENV (same rule as tracking pixel-groups). (b) One provider's HTTP email API — rejected: the owner ordered provider-agnostic SMTP. (c) Forced-2FA by UI gate only — rejected: a restricted session must be enforced server-side or a direct API call bypasses it.
