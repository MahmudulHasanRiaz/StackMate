# ADR-0010: Server-side search — searchable selects + real global search

- **Status:** Accepted (implemented 2026-11-18, search batch — owner rules 2026-11-18 15:56–16:02 +06, Roman Bangla)
- **Context:** Every entity selector in the admin SPA was a native `<Select>` loading the FULL collection via `useAdminList` and rendering every row as an `<option>` — no type-to-search, and the native popup is OS-rendered, so it never opens on the user's extension-driven browser (same defect class as the wizard Price dropdown, 2026-11-17). The header search was quick navigation only — it never searched record data. List endpoints returned full collections with no server pagination and no `q` param (except tickets + leads). The owner set five hard rules: (1) every entity selector searchable + selectable + typable; (2) the header search is a REAL global search bar (results across entities, click → detail page), with quick navigation kept as a section inside it; (3) NO search may miss a result because it sits beyond some loaded amount — every search queries the server/DB over the FULL dataset; (4) filters are searchable too, except a filter that can CONFIRMED never have more than 7–8 options; (5) everything typable and keyboard-usable (arrows + Enter, Esc).

- **Decision 1 — Server-side `q` + `limit` on list endpoints (API spec §18.11):** Shared helpers in `apps/api/src/app.ts` (`parseListQuery` / `applyListLimit` / `includesQuery` / `matchesPhoneQuery`): `q` (trimmed, lowercased) + `limit` (clamped 1..100; absent = no limit). `q` filters: customers (name/email/phone incl. digits-only match on normalized_phone/customer_number/company_name); orders (order_number, public_reference, customer name); products (name/code); licenses (license_number, customer name, product code); subscriptions (subscription_number, customer name); users (name/email); integrated-sites (name/site_key/domains); payment-methods (display_name); payment-providers (display_name); features per product (name/feature_key); packages per product (name). Tickets + leads keep their existing `q` and gain `limit`. `limit` slices AFTER the filter, so a cap can never hide a match. **Why no FTS/trigram index:** the store loads the full table snapshot per request by design (DrizzleStore), so `q` filtering over `store.state` IS filtering over the full dataset — substring matching is sufficient at this scale, and Postgres stays primary with its full power available later. **Caveat (load-bearing): if the store ever paginates at the DB layer, the `q` filters must move into SQL** — the endpoint contract (`?q=` / `?limit=`) does not change.
- **Decision 2 — Global search endpoint (API spec §18.12):** `GET /api/v1/admin/search?q=` → `{ query, groups: [{ key, label, items: [{ type, id, label, sublabel, to }] }] }`, ≤8 items per group. Logic in `apps/api/src/modules/search/service.ts` (`searchGlobal(state, principal, q)`, pure function, unit-testable); app.ts only routes. Groups (permission-gated by the caller's own permissions — a group the caller cannot read is OMITTED, never 403s the whole search): Customers, Orders, Products, Licenses, Subscriptions, Tickets, Leads, Staff, Sites. `q` shorter than 2 chars → empty groups (no full-table dump). Contract in `packages/contracts/src/domains/search.ts` (`GlobalSearchResponse`, `MIN_QUERY_LENGTH = 2`, `MAX_PER_GROUP = 8`), exported from the contracts index. The header search calls it debounced 250ms (⌘K dialog in shell.tsx): entity groups first, then the Pages group (nav + settings + actions, client-side filtered as before). One flat arrow-key list across groups; Enter navigates; Esc closes + clears.
- **Decision 3 — ONE shared `SearchableSelect` combobox (`apps/admin/src/components/primitives.tsx`):** Typable `<input>` trigger wearing the `.sm-select` look (chevron background, text cursor) + portaled listbox reusing `.sm-row-menu` / `.sm-menu-item` (same open/close contract as MenuSelect: click toggles, Esc closes and restores the selected label, outside pointerdown / scroll / resize close, flips above the trigger near the viewport bottom, `--sm-z-popover: 65` so it paints above dialog overlays). Two modes: **server** — `loadOptions(query, signal)`, debounced 200ms, AbortSignal-combined with the 30s client bound in `loadListOptions` (`apps/admin/src/lib/section-kit.tsx`: `?q=&limit=25`, default; `opts.limit` for wider windows); **local** — `options` filtered client-side as you type (small BOUNDED lists only: per-order installments, per-customer contacts, per-product packages/prices/features, server-provided distinct filter values). `leadingOptions`: static first options never filtered (All… / None / Unlinked). `selectedLabel` / `resolveLabel`: the label to show when closed while the value is not among the loaded options (a filter value restored from the URL resolves via the single-record detail endpoint — never a raw id; a 404 falls back to the placeholder). `data` payload on options, handed back as the second `onChange` argument, so auto-fill handlers (ticket linked records, payment-review order/method) can read linked ids without a second fetch. Keyboard: ArrowDown/Up moves, Enter chooses the active option (typing auto-highlights the first match, so Enter picks the top result), Esc closes. `MenuSelect` is now unused by any section (kept in primitives — removing it is a separate cleanup).
- **Decision 4 — What converted and what stayed native (full inventory in PLAN §29):** Converted to SearchableSelect (server mode unless noted): orders wizard customer/product/package (local)/price (local)/feature (local)/payment-method; tickets assignee + customer filters, create customer/assignee/order/subscription/license/product, detail assign; leads site filter/product/assignee; features + packages product pickers; payment-methods provider picker; payment-review order/method/installment (local); integrations assign-product; tracking-config + webhooks site pickers; audit-log action/resource-type/actor-type filters (local — complete distinct sets from the loaded collection); customers split-contact + split-phone (local — per-customer sets). **Stayed native (confirmed ≤8, fixed enums — each recorded in PLAN §29 with its bound):** audit outcome 3, 2FA mode 3, customer type 2, customer status 3, report type 2, TLS mode 3, entitlement period 3, feature value types 4, site environment 3, credential type 2, verify method 3, lead status 5, license status 5, payment-status filter 6+All=7, subscription-status filter 7+All=8, ticket status 5, ticket priority 4, ticket category 5, customer mode 2, item kind 2, price kind 4, plan kind 3, activation mode 3, package price kind 4, interval unit 4, provider type 3, method status 2, method kind 3, account type 3, txn requirement 3, reject reasons 6, product type 7, fulfillment type 4, tracking provider 2, rows-per-page 3. **Any future option added to one of these enums past 8 forces conversion to SearchableSelect.** No schema change, no migration, no color/radius change.
- **Decision 5 — Two bounded exceptions to the hard rule (recorded honestly, not hidden):** (a) **Payment-review order picker** — the "unpaid orders only" filter has no single server-side value (it is payment_status ≠ paid AND status ≠ cancelled; the endpoint filters one `payment_status` at a time), so the loader fetches the first **100** server matches for the typed query and filters unpaid client-side. The typed query narrows first (order number / reference / customer name), so the open order is among the first 100 matches in practice; a server-side `open_only` param is the follow-up if order volume ever makes this matter. (b) **Integrations assign-product** — already-assigned products are filtered out in the loader over the first 25 matches; a site holds only a handful of assigned products, so they cannot crowd out the first 25 matches. Both are documented here because rule (3) is hard — these are the only two places where a client-side filter runs over a capped server window, and both caps are documented with the reason the window cannot hide the wanted record.
- **Decision 6 — Test evidence:** New `apps/api/test/server-search.test.ts` (full dispatcher, real Postgres, own DB `stackmate_test_server_search`): seed 60 customers/products/orders; `q` for the 55th by name → returned (proves beyond-first-page); same by phone fragment; 60 products, `q` for the 55th; `limit` caps AFTER filtering; global search returns grouped results with correct `to` routes + ≤8/group; 1-char query + no-match → empty groups; unauthenticated → 401; `searchGlobal` permission gating at service level (a customers-only principal gets no Orders group). **12/12 pass.** The suite fails pre-fix (no `q` param existed) and passes post-fix.
- **Open / owed:** (a) Live verification of everything in this batch is owed (parent push + browser re-test: type a customer name in the header search, type-to-filter in a selector, the 55th-record case on staging). (b) The two bounded exceptions in Decision 5 — a server-side `open_only` orders filter if order volume grows; nothing else pending. (c) `MenuSelect` is now unused — removal is a separate cleanup, not done here. (d) The features/packages product-picker tables still list every product as a table (not a dropdown) — that is a table, not a selector, and stays as-is; if the product count grows large the picker table needs its own search, recorded here rather than silently assumed fine.
