# ADR-0012: Media thumbnails (browser-side) + fast content endpoint

- **Status:** Accepted (implemented 2026-11-18, thumbnails batch — owner order 2026-11-18 ~20:47 +06, Roman Bangla: "media lybrary te image dekhay khub beshi slow load hoy. kno?!" + go-ahead 2026-11-18 22:28: "pblm thakle fix kno korba na? image optimize er jonno sherp use er sujug thakle smartly setaw koro" — "sherp" = Sharp, use it smartly IF there is an opportunity)
- **Context:** ADR-0011 Decision 5 deliberately shipped the media library with NO thumbnails: every grid/picker cell downloaded the FULL original through `GET /api/v1/admin/media/:id/content`, which buffered the whole R2 object via `arrayBuffer()` (no streaming, no Range, no ETag) with `Cache-Control: private` (no edge cache). The grid shows ~160px cells but downloaded the 1.1 MB original (staging's only file, 1254×1254) — ~50× more pixels than displayed; the 32px list thumb downloaded the same 1.1 MB. The same defect made video `preload="metadata"` download whole videos. The owner reported the library as "khub beshi slow" (very slow) and ordered a fix, explicitly asking whether Sharp could be used smartly.

- **Decision 1 — Sharp has NO opportunity on the Workers API (verified from Sharp's own docs, not assumed).** Sharp's install documentation (https://sharp.pixelplumbing.com/install, read 2026-11-18) states the prerequisite as a "Node-API v9 compatible runtime e.g. Node.js >= 20.9.0" and ships prebuilt binaries only for macOS / Windows / Linux / FreeBSD (plus a WASM build, `@img/sharp-wasm32`, whose single-threaded use on Workers is unsupported — it needs multi-threaded Wasm). Cloudflare Workers runs V8 isolates with no native-binary support, and the staging/production API runs there. Corroborated by secondary sources (Workers runs no native modules; the edge options are Cloudflare Images, a WASM pattern, or deferring to a Node.js worker). Conclusion: NO `sharp` dependency anywhere in the repo, no server-side image pipeline on the API. If Sharp is ever wanted, it belongs in a Node.js worker (Docker/VPS deploy target, PLAN §33) — a separate decision, not this batch.

- **Decision 2 — Browser-side thumbnail generation at upload (the pipeline).** The admin SPA generates thumbnails with native browser APIs (`createImageBitmap` + canvas, `imageOrientation: "from-image"` so phone JPEGs don't come out sideways, falling back to plain `createImageBitmap` on old browsers): one decode, two resizes — 320px max (grid / picker cells) + 64px max (32px list thumb) — encoded WebP q80 (`apps/admin/src/lib/thumbnails.ts`: `generateThumbnails`, `canGenerateThumbnail`). Raster images only (PNG/JPEG/WebP/GIF — never SVG, which is vector and usually small); never upscales; any variant `>=` the original size is dropped; any failure (old browser, no canvas/WebP, decode error) returns null and the upload proceeds WITHOUT thumbnails — never throws, never blocks. Both upload spots generate: the library upload dialog (`sections/media-library.tsx` `handleUpload`) and the picker upload (`components/media-picker.tsx` `handleFiles`). A 1.1 MB photo's grid cell now loads ~20 KB instead of 1.1 MB.

- **Decision 3 — Thumbnails are sibling objects, same driver, deterministic keys (migration 0013).** The server stores each thumbnail as a sibling R2/Local object under a deterministic key derived from the original (`apps/api/src/platform/storage/media-validation.ts`: `mediaThumbnailKey` → `<base>-thumb-320.webp` / `<base>-thumb-64.webp`, always `.webp`), so a regenerate overwrites the same object and a delete removes both without a second lookup. Migration 0013 adds 4 nullable columns to `media_assets` (`thumb_object_key`, `thumb_small_object_key`, `thumb_byte_size`, `thumb_small_byte_size` — additive, expand-and-contract; pre-0013 rows simply have no thumbnail). Thumbnails follow the row's driver (R2 or Local — same `resolveStorageDriver` path). `uploadMediaAsset` accepts optional `thumbnails { thumb?, small? }`, each validated as `image/webp` via `verifyMediaBytes` — a bad thumbnail is DROPPED and the original upload still succeeds (never fail an upload over a thumbnail); on row-insert failure the original + thumbs are deleted (same orphan cleanup as ADR-0011, extended). `deleteMediaAsset` deletes both thumb objects (best-effort). Contract: `MediaAssetView` gains `thumb_url` / `thumb_small_url` (`/api/v1/admin/media/:id/content?variant=thumb|small`), null when absent — the UI falls back to `content_url` everywhere, never a broken image.

- **Decision 4 — Regenerate endpoint = the backfill (no server pipeline invented).** `POST /api/v1/admin/media/:id/thumbnail` (`media.manage`, multipart `thumbnail` + `thumbnail_small`, audited `media.thumbnail_regenerated`) regenerates thumbnails for an existing image. Unlike upload, a bad thumbnail IS the error here (415 from `verifyMediaBytes` — the whole point of the call is the thumbnail); non-raster MIMEs (incl. SVG) → 422; no thumbnail file at all → 422. The detail drawer shows a "Generate thumbnail" button when an image has no thumbnail (raster, non-SVG): it loads the original once via `fetchMediaFile`, generates in the browser, POSTs, updates the drawer + invalidates the list. This is the documented manual step for the ONE existing staging file ("Ivory R Monogram with Golden Accent-retest.png") — the owner opens it and taps the button. No server-side backfill job, no Sharp, no new binding.

- **Decision 5 — Content endpoint: stream + Range + ETag (API spec §18.13).** `GET /api/v1/admin/media/:id/content` no longer buffers: `StorageDriver.getStream(key, range?)` passes the range straight to R2 (`bucket.get(key, { range: { offset, length } })` — Cloudflare R2 Workers API ranged reads return `R2ObjectBody` with a `.body` stream + `.range`) or to `FileHandle.createReadStream({ start, end })` on the Local driver; total sizes come from the DB row, so no `head()` call is needed. `?variant=thumb|small` selects the thumbnail object (unknown variant → 422; variant requested but no thumbnail stored → 404 "Thumbnail not available for this asset."). `ETag` is derived from the stored checksum (`"<sha256>"`, `"<sha256>-thumb-320"`, `"<sha256>-thumb-64"`); `If-None-Match` match (or `*`) → 304 with no body. `Range: bytes=start-end` is parsed server-side (suffix `bytes=-N` and open-ended `bytes=N-` supported, end clamped to size−1; multi-range ignored → full 200, per RFC 7233); a satisfied range → 206 + `Content-Range: bytes start-end/size`; an unsatisfiable start → 416 `RANGE_NOT_SATISFIABLE` with `Content-Range: bytes */size` (new error code in `packages/contracts/src/common/envelopes.ts`). Every response carries `Accept-Ranges: bytes` + `Content-Length`. Auth (`media.view`) + the SVG sandbox CSP are unchanged. Video `preload="metadata"` now downloads only the requested range instead of the whole file.

- **Decision 6 — Hygiene + what stays the same.** Grid / picker / list images use `thumb_url` / `thumb_small_url` with `content_url` fallback, plus `decoding="async"` and explicit `width`/`height` (dimensions already in the API response). The detail drawer and downloads keep the FULL original. No thumbnails for non-image files (video/audio/docs keep current behavior — their metadata requests are fixed by Range, not by thumbnails). Permissions (`media.view` / `media.manage`), the R2/Local driver strategy, upload validation (MIME + magic bytes, caps), and audit logging for upload/delete are all unchanged. No new dependencies (§5: nothing added — the whole pipeline is browser-native + the R2 ranged-read API).

- **Decision 7 — What changes if the owner later enables Cloudflare Images (`env.IMAGES`).** The contract (`thumb_url` / `thumb_small_url`) and the UI do NOT change — only the producer: the API would generate variants server-side via the Images binding (e.g. an `images.transform` / variant call at upload, or a Cloudflare Images variant URL stored as the thumb URL) instead of trusting browser-generated bytes, and the regenerate endpoint would call Images instead of accepting multipart thumbnails. The migration columns stay valid (they would record the Images-variant object keys or the variant URLs' backing keys). Until then, browser-side generation is the pipeline and nothing in the API assumes an Images binding exists.

- **Decision 8 — Test evidence:** `apps/api/test/media-library.test.ts` gains 6 tests (upload with thumbs → URLs set + variant content returns the exact WebP bytes, smaller than the original, with `-thumb-320`/`-thumb-64` ETags; Range 206 + Content-Range for first-bytes / suffix / open-ended, 416 with `bytes */20`; If-None-Match 304 incl. `*`, miss → 200; upload without thumbs → null URLs + variant 404, bad thumb on upload dropped + upload still 201; regenerate adds thumbs to a thumb-less asset, 422 for SVG, 415 for bad thumb bytes; delete removes both thumb objects — `bucket.get` → null). WebP fixture is a 12-byte RIFF/WEBP header + "A" fill (pure ASCII + NULs so the text helper round-trips it). **Full verify 2026-11-18:** `verify-batch1.sh` exit 0 — vitest **289/289, 37 files** (was 283/283; media file 20/20 incl. the 6 new), tsc api + admin, vite build, lint **235 files**, check-migrations **81 tables / 14 migrations**, wrangler dry-run staging. jsdom smoke **259/259** (was 257; 2 new checks: grid cell uses `?variant=thumb`, list thumb uses `?variant=small`). Sidebar-hover **44/44**, responsive **74/74**, real-browser **37/37**, dashboard **23/23**. **Three real bugs found + fixed by these tests:** (a) `parseHttpRange` checked `end < start` before `start >= size`, so an open-ended `bytes=<size>-` returned 200 instead of 416 — reordered. (b) `createImageBitmap` was called with `imageOrientation: "flip"` — the type only allows `"from-image"` (EXIF) / `"flipY"` / `"none"` — fixed to `"from-image"`. (c) A `RegExpExecArray` → tuple cast + two `assert.ok(…, header ?? null)` messages failed strict tsc — fixed to indexed access + string messages. One flaky failure seen once in a parallel vitest run (`worker-1101-repro`: a stray backend from another file's pool at count time) — passes 4/4 in isolation, unrelated to this batch (no pool/dispatch code touched); the rerun passed 289/289.
